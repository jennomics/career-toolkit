# Intelligence layer upgrade: skill taxonomy + executive prompts + generic resume mode

This change adds two major capabilities to the career toolkit. First, a static skill taxonomy with 80+ canonical skills and 150+ variant mappings that normalizes messy job/experience skill records into a hierarchical structure (Hard Skills / Soft Skills > subcategories > specific skills). Second, a rewrite of all four LLM resume prompts to adopt executive-level positioning language, plus a new "generic resume" mode that optimizes a single resume for coverage across all saved jobs, with a scoring endpoint that evaluates how well a resume text matches each job's skill requirements.

The taxonomy is entirely in-memory (a static TypeScript data structure), with a POST endpoint to back-fill normalizedName/category fields on existing DB records. The coverage scorer uses substring matching with a hand-rolled abbreviation map. The LLM prompts shift from generic resume-writer instructions to strategic-narrative framing with verb hierarchies and outcome-oriented language.

Watch for: the normalization endpoint updates records one at a time with no batching or transaction (confirmed), the coverage scorer duplicates variant logic already in the taxonomy module instead of reusing it (confirmed), and substring matching without word boundaries will inflate coverage scores for short skill names like "go", "ai", "ci" (confirmed).

## High-level view

The taxonomy lives entirely in `src/lib/skill-taxonomy.ts` as a static constant plus derived lookup maps. The normalize endpoint iterates all skill records and writes back normalized names sequentially — functional for small datasets but will hit timeouts as data grows.

The coverage scorer in `/api/resume/coverage` implements its own substring + abbreviation matching rather than consuming the taxonomy's normalization layer. This means the two variant maps will drift over time as one gets updated and the other doesn't. The matching uses `includes()` with no word-boundary awareness, so "go" matches "google" and "algorithm" — this will inflate scores for short skill names.

The generic resume mode re-uses the existing generate endpoint with a `mode` parameter that switches the system prompt and constructs a different user prompt aggregating all saved jobs. The prompt tells the LLM it's showing "ALL SAVED POSITIONS" but actually caps at 20 job summaries, while keyword frequency is computed from the full set — a mismatch that could confuse the model when totals are high.

<details>
<summary>Issues (5)</summary>

1. **Normalize endpoint has no batching or transaction** — Each skill record is updated with an individual `await prisma.update()`. For hundreds of records this will be slow and risks partial completion on timeout. Batch updates using `prisma.$transaction` or `updateMany` where possible.
2. **Coverage scorer duplicates variant logic** — `getSkillVariants()` in the coverage route reimplements abbreviation mappings that already exist in `skill-taxonomy.ts`. Use `normalizeSkillName` from the taxonomy module so variant mappings stay in one place.
3. **Substring matching inflates scores for short skills** — `resumeLower.includes("go")` matches "google", "algorithm", "cargo", etc. Use word-boundary regex (`\bgo\b`) or restrict matching to skill-like contexts.
4. **No DB migration shipped** — Schema adds columns (`normalizedName`, `category`) and a new model (`SkillTaxonomy`) but there's no migration file. Works with `prisma db push` for this deployment model but means no rollback path if the schema change causes issues.
5. **Coverage scorer gives 100% to jobs with zero skills** — Jobs that have no extracted skills get score 100 with empty matchedSkills/missedSkills. This inflates the per-job display and misleads users about coverage quality. These jobs should be excluded from scoring or scored as N/A.

## Sequential normalization without batching

The `/api/skills/normalize` POST handler fetches all `JobSkill` and `ExperienceSkill` records, then updates each one individually in a serial loop:

```typescript
for (const skill of jobSkills) {
  // ... compute normalizedName and category
  await prisma.jobSkill.update({
    where: { id: skill.id },
    data: updateData,
  });
}
```

There's no transaction wrapping the loop, so if the function times out mid-way, some records are normalized and others aren't — the user sees a failure but the data is partially mutated with no indication of which records were processed. A `prisma.$transaction` around batched updates (or grouping records by their normalized result and using `updateMany` with a `where: { id: { in: [...] } }` clause) would provide both performance and atomicity.

## Coverage scorer's parallel variant universe

The coverage route implements its own `getSkillVariants()` function with a hardcoded `abbreviationMap`:

```typescript
const abbreviationMap: Record<string, string[]> = {
  "javascript": ["js", "ecmascript"],
  "typescript": ["ts"],
  "machine learning": ["ml", "deep learning"],
  // ...22 entries
};
```

Meanwhile, `src/lib/skill-taxonomy.ts` already maintains a comprehensive normalization map (150+ mappings) with the same purpose. The two will diverge as maintainers add variants to one but not the other. The coverage endpoint should call `normalizeSkillName()` on both the resume tokens and the job skill names before comparing, eliminating the need for a separate variant map entirely.

## Substring matching false positives

The `isSkillInResume` function checks `resumeLower.includes(skillLower)`. For short or common skill names this produces false positives:

- "go" matches "google", "algorithm", "ergonomic", "cargo"
- "ai" matches "maintain", "contain", "detail"
- "ci" matches "efficient", "sufficient"

The multi-word path has the same issue: splitting "data analysis" into ["data", "analysis"] and checking each with `includes` would match "metadata" + "paralysis" independently.

Word-boundary matching (`new RegExp(\`\\b${escaped}\\b\`)`) would eliminate most of these. The performance cost of regex is negligible since the resume text is scanned once per skill.

## Jobs with no skills score 100%

```typescript
if (jobSkills.length === 0) {
  return { ..., score: 100, matchedSkills: [], missedSkills: [] };
}
```

The overall score weights by skill count (`totalSkillChecks`), so zero-skill jobs contribute nothing to the denominator — but they still appear in the per-job list at 100%, which is confusing. Excluding them from `jobScores` output or marking them explicitly as "no skills to evaluate" would be clearer.

## Prompt construction gap in generic mode

In generic mode, the user prompt includes up to 20 job summaries:

```typescript
const jobSummaries = jobs.slice(0, 20).map((job) => { ... });
```

But `topKeywords` is computed from ALL jobs (no slice). The prompt labels the section "ALL SAVED POSITIONS (${jobs.length} jobs to cover)" — showing the real count (e.g., 50) while only providing 20 summaries. If a user has 100+ saved jobs, the keyword frequency data reflects all of them while the LLM only sees 20 for context. The label should either say "top 20 of N positions" or the slice should match the stated count.
