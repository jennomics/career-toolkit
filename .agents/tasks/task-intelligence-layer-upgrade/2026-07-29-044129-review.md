# Intelligence layer upgrade: taxonomy + executive prompts + generic resume (v2)

The v1 concerns — missing transaction, duplicated variant logic, substring false positives, zero-skill inflation, and misleading prompt label — have all been addressed. The normalize endpoint now collects operations into a `prisma.$transaction` array. The coverage scorer delegates to `normalizeSkillName` and `getCanonicalAliases` from the taxonomy module instead of maintaining its own abbreviation map. Matching uses word-boundary regex throughout. Zero-skill jobs are excluded from scoring. The generic-mode prompt correctly labels the section as "TOP 20 OF N" when jobs exceed 20.

Watch for: multi-word fallback matching can still produce false positives for common word combinations (likely), `getCanonicalAliases` performs a full taxonomy tree traversal per skill per call with no caching (confirmed), and the transaction size is unbounded — a user with thousands of skill records will hit Prisma's parameter limit (possible).

## High-level view

The coverage scorer's multi-word fallback — checking that all words longer than 2 characters appear independently anywhere in the resume — is the widest remaining aperture for false positives. Skills like "data engineering" will match a resume containing "data governance" and "software engineering" in unrelated paragraphs.

The normalize endpoint's `$transaction` wrapping provides atomicity, but Prisma transactions have a default limit of ~32k parameters (depending on the database adapter). Each update contributes roughly 3 parameters (id, normalizedName, category), so 10k+ records would exceed the limit. Batching into fixed-size chunks would remove this ceiling.

`getCanonicalAliases` iterates the full taxonomy tree (2 categories x 14 subcategories x ~6 skills = ~170 iterations) on every call. For a resume scored against 50 jobs with 10 skills each, that's 85k iterations per coverage request. A pre-computed `Map<string, string[]>` at module level — matching the existing pattern for `normalizationMap` — would make it O(1).

## Multi-word fallback matching

The coverage scorer's final matching tier fires when exact regex, canonical-form regex, and alias checks all miss:

```typescript
const words = skillLower.split(/\s+/).filter((w) => w.length > 2);
if (words.length > 1) {
  const allPresent = words.every((word) => {
    const wordEscaped = escapeRegex(word);
    const wordRegex = new RegExp(`\\b${wordEscaped}\\b`);
    return wordRegex.test(resumeLower);
  });
  if (allPresent) return true;
}
```

The scenario: a skill like "data engineering" where the resume mentions "data governance" and "software engineering" separately. Both "data" and "engineering" pass word-boundary checks independently. The `w.length > 2` filter removes trivial words but not meaningful ones appearing in unrelated contexts.

Requiring proximity (both words within N words of each other) or restricting this path to 3+ word skills would tighten accuracy without eliminating legitimate fuzzy matches.

## Alias lookup efficiency

```typescript
function getCanonicalAliases(canonicalName: string): string[] {
  const taxonomy = getTaxonomy();
  for (const category of taxonomy.categories) {
    for (const subcategory of category.subcategories) {
      for (const skill of subcategory.skills) {
        if (skill.canonicalName === canonicalName) {
          return skill.aliases;
        }
      }
    }
  }
  return [];
}
```

The taxonomy module already builds a `normalizationMap` (alias-to-canonical) at module load. The reverse map (canonical-to-aliases) should be built the same way and exported, making `getCanonicalAliases` a one-liner lookup instead of a tree traversal.
