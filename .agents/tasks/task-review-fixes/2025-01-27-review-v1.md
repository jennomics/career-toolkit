# Security hardening, analytics corrections, and data exposure fixes

This commit addresses eleven review findings spanning authentication posture (GC fail-closed, middleware gating, dead auth removal), analytics accuracy (event-based conversion rates, current-stage time-in-stage), data integrity (transaction atomicity, status validation, SQL injection surface), eval correctness (assertion scoping), and data exposure (identity fixtures, company references). The approach is defensive: auth gates now exist at both middleware and handler level for GC routes, analytics switch from snapshot-only to event-history-based computation, and the Prisma proxy properly binds `this` so `$transaction` calls work.

Watch for: the skills `deleteMany` in the PATCH handler runs outside the transaction when both skills and status change simultaneously (confirmed); the fallback conversion-rate path lumps all terminal-status jobs into the "applied" bucket which is a rough approximation that skews early-stage rates (likely); the integrity route's GC_AUTH_TOKEN warning message is now factually wrong (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The security fixes establish a consistent fail-closed posture: middleware rejects GC requests without a valid bearer token before they reach the handler, and the handler independently validates (belt-and-suspenders). The `requireServiceToken` utility and `requireAuth` removal align the auth module with what the middleware already enforces.

The Prisma proxy fix binds method references to the real client, which was required for `$transaction` (and any other method relying on `this`). Without this, the transaction-atomicity fix for status changes would have silently broken at runtime.

Conversion-rate analytics now compute from event history when available, propagating implicit stage reachability backward. The fallback snapshot path adds terminal statuses to the "applied" bucket — a lossy approximation that overstates early-stage difficulty and understates late-stage drop-off.

The PATCH handler wraps status update + event creation in `$transaction`, but the preceding `jobSkill.deleteMany` call runs outside that transaction. A failure between the skill deletion and the transactional write leaves the job with its skills deleted but its status unchanged.

## Skills deletion outside the transaction boundary

In `src/app/api/jobs/[id]/route.ts`, when a PATCH includes both `skills` and a `status` change, the flow is:

```typescript
if (skills !== undefined) {
  await prisma.jobSkill.deleteMany({ where: { jobId: id } });
}
// ... later ...
if (status !== undefined && status !== currentJob.status) {
  const [updatedJob] = await prisma.$transaction([
    prisma.job.update({ ... }),
    prisma.applicationEvent.create({ ... }),
  ]);
  return NextResponse.json(updatedJob);
}
```

The `deleteMany` is not inside the `$transaction`. If the transaction fails (constraint violation, connection drop), the skills are already deleted but the status and event are not written. This leaves the job in an inconsistent state: skills gone, old status retained. The fix is either to use an interactive transaction that wraps the entire mutation, or to move the `deleteMany` into the array-style transaction (Prisma supports it).

## Fallback conversion-rate heuristic

The snapshot fallback in `computeConversionRates` adds all rejected/withdrawn/closed counts to the "applied" bucket:

```typescript
for (const t of terminalStatuses) {
  if (augmented[t]) {
    augmented["applied"] = (augmented["applied"] || 0) + augmented[t];
  }
}
```

A job that was rejected at "final-round" gets counted as if it only ever reached "applied", deflating the applied-to-screening conversion rate (denominator grows) while having no effect on the screening-to-interviewing rate (the rejected job isn't added there). In practice this overstates the difficulty of early stages and understates the drop-off at later stages. The event-based path handles this correctly, so the fallback is only relevant during the transition period before event history accumulates.

## Integrity route message inaccuracy

In `src/app/api/integrity/route.ts` line ~130:

```typescript
if (!hasGcToken) warnings.push("GC_AUTH_TOKEN not set (groundcrew API is open/unauthenticated)");
```

With the middleware now failing closed, the GC API is *inaccessible* when the token is missing in production, not "open". The warning should read something like "GC_AUTH_TOKEN not set (groundcrew API will reject all requests in production)".
