# Security hardening: auth gate, demo mode, LLM cost controls, error sanitization

This change adds a security and operational safety layer across a Next.js career toolkit app. A Next.js middleware enforces bearer-token auth on all API routes (or blocks mutations when in demo mode), a standardized error response format prevents leaking internal details, and a set of LLM guard utilities (input length, concurrency semaphore, daily budget, timeout) protect the OpenAI integration. The `schema-push.yml` workflow is replaced by a proper `migrate.yml` that uses `prisma migrate deploy`. A 89-test Vitest suite covers the new security utilities, parsing logic, and skill normalization.

Watch for: Rate limiters are defined but never wired into any request path (confirmed). LLM guards only protect `llmParseJob` — six other OpenAI call sites have no input-length, timeout, budget, or concurrency controls (confirmed). The middleware reuses the same `Authorization` header for both `AUTH_SECRET` and `SERVICE_TOKEN` checks, meaning a service caller to `/api/sentinel` must present the regular auth secret AND the service token must match the same header value — if they differ, access is impossible (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The middleware in `src/middleware.ts` is the single enforcement point for auth and demo-mode mutation rejection. It has a token-resolution conflict: when both `AUTH_SECRET` and `SERVICE_TOKEN` are configured with different values, requests to sentinel/integrity pass the AUTH_SECRET check first, then fail the SERVICE_TOKEN check against the same header — making these routes unreachable. This needs a design decision (separate header, exempt these routes from AUTH_SECRET, or require both tokens match).

Rate limiting (`src/lib/rate-limit.ts`) and LLM guardrails (`src/lib/llm-guard.ts`) are incomplete in their integration. The rate limiters are exported but never called from the middleware or any route handler. The LLM guards (input validation, budget, concurrency, timeout) are only applied in `llmParseJob` — the six other routes that directly instantiate OpenAI clients (`resume/generate`, `resume/generate-company`, `resume/project/[id]/build`, `cover-letter`, `improve`, `experience/extract`, `gap-analysis`) have none of these protections. A single expensive gpt-4o resume-generation call can run indefinitely without a timeout and not count against the daily budget.

Every API route's catch block now goes through `formatErrorResponse`, which wraps unknown errors in a generic `INTERNAL_ERROR`. The inconsistency is that several routes still return inline `{ error: "..." }` strings for validation errors (e.g., profile/metrics POST) rather than the structured `{ error: { code, message, requestId } }` shape, so clients must handle both formats.

The demo-mode env var is split: server-side reads `DEMO_MODE`, client-side `DemoBanner.tsx` reads `NEXT_PUBLIC_DEMO_MODE`. The deployer must set both variables — there's no documentation or runtime check linking them.

<summary>Details</summary>

## Token conflict on sentinel/integrity routes

The middleware processes auth sequentially: first it checks `AUTH_SECRET` against the `Authorization` header (line 45-58), returning 401 if it doesn't match. Only afterward does it check `SERVICE_TOKEN` against the same header for sentinel/integrity POST (line 61-78). If a service caller sets `Authorization: Bearer <SERVICE_TOKEN>` and `SERVICE_TOKEN !== AUTH_SECRET`, the request is rejected at the first check before reaching the service-token logic.

```
Request to POST /api/sentinel
  Authorization: Bearer <SERVICE_TOKEN>

-> Step c: token !== AUTH_SECRET -> 401 (never reaches step d)
```

The workaround — requiring `SERVICE_TOKEN === AUTH_SECRET` — defeats the purpose of having two separate tokens. One fix is to skip the `AUTH_SECRET` check for sentinel/integrity paths and only require the service token there.

## Rate limiting: defined, never enforced

`src/lib/rate-limit.ts` exports two pre-configured rate limiters — `llmRateLimiter` (10/min) and `generalRateLimiter` (100/min). Neither is imported or called by the middleware, any API route, or any other module. A grep for usage outside the definition file and its test returns zero results. The feature is entirely inert.

## LLM guards applied only to parse-job

`llmParseJob` in `src/lib/llm-parse-job.ts` demonstrates the full guard chain: `validateInputLength` -> `checkDailyBudget` -> `llmSemaphore.acquire` -> `createAbortSignal` -> `logLLMCost` -> `llmSemaphore.release`. The other routes that create their own `new OpenAI(...)` client and call `chat.completions.create` directly have none of these protections:

- `resume/generate/route.ts` — generates full resumes (gpt-4o-mini)
- `resume/generate-company/route.ts` — company-targeted generation
- `resume/project/[id]/build/route.ts` — builds resume from highlights (gpt-4o)
- `resume/project/[id]/cover-letter/route.ts` — cover letter (gpt-4o)
- `resume/project/[id]/improve/route.ts` — bullet improvement (gpt-4o)
- `experience/extract/route.ts` — experience extraction from raw text
- `resume/gap-analysis/route.ts` — LLM gap analysis

The most expensive of these (gpt-4o with large context) are exactly the ones that need budget tracking and concurrency limiting most.

## Error format inconsistency in validation responses

Several routes still return ad-hoc validation error shapes that don't match the public contract established by `formatErrorResponse`:

```typescript
// profile/metrics POST
return NextResponse.json({ error: "Label and value are required" }, { status: 400 });

// resume/generate-company POST
return NextResponse.json({ error: "companySlug (string) is required" }, { status: 400 });
```

These return `{ error: string }` rather than `{ error: { code, message, requestId } }`. Clients consuming the API must handle two different error shapes depending on whether the error is a validation rejection or a caught exception.

## In-memory budget tracking volatility

`dailySpend` in `llm-guard.ts` is module-level state. In a serverless or edge-function deployment (which Next.js App Router can use), each invocation may be a cold start with `dailySpend.totalUsd = 0`. Even in a long-running Node server, a process restart resets the counter. The $5/day limit is a best-effort heuristic rather than a hard ceiling.

## Middleware not directly tested

The middleware logic — especially the token conflict between `AUTH_SECRET` and `SERVICE_TOKEN` — has no dedicated test. The `auth.test.ts` file tests the utility functions in `src/lib/auth.ts` (which are not actually used by the middleware; the middleware reimplements the same logic inline). Adding a middleware integration test would catch the sequential-check bug.
