# Voice Corpus and Document Ingestion Pipeline (v2)

Adds document storage, paragraph-level passage chunking with LLM-inferred topics, topic-based retrieval at generation time, a WritingSample migration path, and a client-side management UI. All six issues from the v1 review have been addressed: POST now triggers ingestion, topic derivation uses vocabulary words only, `inferTopics` logs on parse failure, ingestion uses `Promise.allSettled` with a semaphore, migration checks both title and content for idempotency, and DELETE relies on schema cascade.

Watch for: `Promise.allSettled` in `ingestDocument` silently drops individual chunk failures — a passage that fails topic inference AND db create simply vanishes with no record (likely); the POST handler awaits ingestion synchronously, so upload latency scales linearly with passage count at ~1s per chunk (confirmed).

**Verdict**: APPROVED

## High-level view

Ingestion now runs concurrently with semaphore gating. The tradeoff is that `Promise.allSettled` discards individual rejections — if a chunk's `processChunk` throws after the semaphore acquire (e.g., a Prisma create failure), that passage is lost without a log entry. For a system where the entire document can be re-ingested idempotently, this is acceptable but worth knowing.

The POST handler awaits `ingestDocument` before returning 201, which means upload latency includes all LLM calls (serialized by the semaphore). For a 20-passage document this could be 10-20 seconds. The UI shows only "Uploading..." with no progress indicator, so the user sees a long hang.

The outer catch in `assembleContext` around voice retrieval only fires for bugs in the topic-derivation code above the `retrievePassages` call, since `retrievePassages` itself never throws. This is narrow but real protection against vocabulary being undefined.

## Concurrent ingestion and failure visibility

The `processChunk` function acquires the semaphore, calls `inferTopics`, then calls `prisma.voicePassage.create`. If the create call throws (network blip, unique constraint in a future schema change), the `finally` block releases the semaphore but the rejection is swallowed by `Promise.allSettled`. The document appears fully ingested — no error surfaces to the caller, the passage count is simply lower than expected.

```typescript
await Promise.allSettled(chunks.map(processChunk));
// No inspection of results — rejected promises are invisible
```

A one-line improvement: inspect the settled array and `console.warn` any rejections with the chunk index and error message. The user then has a signal that re-ingestion is needed.

## Upload flow timing

The POST handler calls `await ingestDocument(document.id)` synchronously before returning 201. The semaphore serializes LLM calls, so N passages means N sequential round-trips to GPT-4o-mini. The response time scales linearly with document length.

The UI's `handleSubmit` shows "Uploading..." during this entire window with no timeout, abort controller, or intermediate feedback. For documents that chunk into 15+ passages, this will feel broken to users expecting sub-second responses.

## Test coverage gaps

Not tested: API route validation logic (invalid enums, missing fields, PATCH with empty body), the migration script against multiple profiles with duplicate titles, UI component behavior (no component tests), or the `assembleContext` voice-corpus integration at the integration level.
