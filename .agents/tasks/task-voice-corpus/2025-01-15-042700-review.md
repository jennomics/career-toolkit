# Voice Corpus and Document Ingestion Pipeline

Adds a document-level storage and passage-level retrieval system for the user's own writing. Documents are uploaded via API, chunked into paragraphs, tagged with LLM-inferred topics, and retrieved by topic overlap during generation context assembly. The existing `WritingSample` model is bridged via a one-time migration script.

Watch for: topic inference silently returning empty arrays on LLM failure leaves passages unretrievable (confirmed); sequential per-passage LLM calls in `ingestDocument` will be slow for large documents (confirmed); the voice-corpus context block in `assembleContext` derives topics from a naive word-slice heuristic that won't match the hyphenated tags `inferTopics` produces (confirmed); the POST endpoint creates documents but never triggers ingestion, so passages are never created until something else calls `ingestDocument` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The POST route validates required fields and enum values but does not call `ingestDocument`, meaning uploaded documents have zero passages until an external step triggers ingestion. This is the largest functional gap in the feature.

Topic inference calls GPT-4o-mini per passage serially. The silent fallback to empty topics on parse failure means a passage exists but is invisible to retrieval — no log, no retry, no user-visible indication.

Retrieval filters to `speakerIsUser: true` AND `sourceDocument.authorship = "user-authored"`, ranks by topic-match count, and fails open (returns `[]` on error rather than blocking generation).

The context assembly integration in `assembleContext` derives voice topics by taking vocabulary words and slicing the first three words of each hiring question joined with hyphens. This ad-hoc approach is unlikely to produce tags that match the structured hyphenated phrases GPT-4o-mini generates during ingestion (e.g., "project-management" vs "what-are-your"). If vocabulary is empty, retrieval returns nothing despite a rich corpus.

The WritingSample migration is idempotent via title-matching but title collisions would cause skips. The `getVoiceGuidance` deprecation warning is in place.

<details>
<summary>Issues (6)</summary>

1. **POST /api/documents never ingests** — A newly uploaded document has no passages because `ingestDocument` is not called. Either call it in the POST handler or expose an explicit ingest endpoint.
2. **Topic mismatch between ingestion and retrieval** — `assembleContext` derives topics via naive word-slicing (`q.question.toLowerCase().split(" ").slice(0, 3).join("-")`), which will rarely match the semantic tags GPT-4o-mini produces. Use an LLM call or a shared vocabulary to derive retrieval topics.
3. **Silent empty-topic fallback** — When `inferTopics` fails to parse the LLM response, the passage is created with `topics: []` and becomes unretrievable. Log the failure or retry.
4. **Sequential ingestion per passage** — `ingestDocument` awaits `inferTopics` + `prisma.create` in a loop. For a 20-passage document this means 20 serial LLM calls. Use `Promise.all` with concurrency control or batch creates.
5. **Migration idempotency by title is fragile** — Two WritingSamples with the same title would collide. A dedicated `migratedFromId` field on `SourceDocument` would be more robust.
6. **DELETE cascades manually despite schema onDelete** — The `[id]/route.ts` DELETE handler manually deletes passages then the document, but the schema already declares `onDelete: Cascade` on the relation. The manual delete is redundant (harmless but misleading).

<summary>Details</summary>

## Ingestion gap in the upload flow

The POST handler at `/api/documents/route.ts` creates the `SourceDocument` row and returns 201, but never calls `ingestDocument`. The spec states that passage chunking happens at upload time. The UI's document detail view shows "No passages extracted yet. Run document ingestion to create passages." — this message implies ingestion is a separate action, but the spec doesn't describe a separate trigger.

```typescript
// POST handler ends here — no ingestion
const document = await prisma.sourceDocument.create({ data: { ... } });
return NextResponse.json(document, { status: 201 });
```

Either the POST handler should call `ingestDocument(document.id)` (and handle the cost of serial LLM calls), or there needs to be an explicit `/api/documents/[id]/ingest` endpoint the UI calls after upload.

## Topic derivation mismatch in context assembly

In `src/lib/generation/context.ts`, the voice-corpus block derives topics like this:

```typescript
const voiceTopics = [
  ...decomposition.vocabulary.map((v) => v.toLowerCase()),
  ...mappedQuestions.map((q) => q.question.toLowerCase().split(" ").slice(0, 3).join("-")),
].filter((t) => t.length > 0);
```

The vocabulary mapping is reasonable — decomposition vocabulary might include terms like "leadership" that match ingested tags. But the question-derived topics take the first three words of a question (e.g., "what-are-your", "describe-a-time") and join them with hyphens. These will never match tags like "team-leadership" or "data-analysis" that GPT-4o-mini assigns during ingestion.

The retrieval call uses `hasSome`, so even one vocabulary term matching is enough to surface a passage. But if vocabulary is empty (plausible for a simple job posting), retrieval returns nothing despite a rich corpus. The question-derived entries contribute zero matches.

## Silent fallback in topic inference

`inferTopics` catches JSON parse failures and returns `[]`:

```typescript
} catch {
  return [];
}
```

A passage with `topics: []` will never satisfy `hasSome` in retrieval. The ingestion succeeds silently — there's no log, no retry, no indication that a passage is orphaned. For a corpus that might have 50-100 passages, losing a few to silent LLM failures degrades retrieval quality without the user knowing.

## Sequential LLM calls during ingestion

`ingestDocument` processes passages in a `for...of` loop, awaiting each `inferTopics` call:

```typescript
for (const chunk of chunks) {
  const topics = await inferTopics(chunk);
  await prisma.voicePassage.create({ ... });
}
```

For a 10-page document that chunks into 20+ passages, this means 20+ sequential GPT-4o-mini calls (each ~500-1000ms). Total ingestion time could reach 20-40 seconds. Batching with `Promise.allSettled` using a concurrency limiter (the codebase already has `llmSemaphore`) would be the natural fix.

## Migration idempotency and collision risk

The migration checks for existing documents by matching on `{ title, category: "work-artifact", authorship: "user-authored" }`. If two WritingSamples share the same title, the second one will be skipped as "already migrated" even though it hasn't been. A `migratedFromSampleId` field on SourceDocument would provide exact deduplication.

The migration uses `sample.createdAt` as `documentDate`, which is the database insertion timestamp rather than when the writing was actually produced. All migrated documents will have recent dates regardless of when the content was written.

## Retrieval log double-logging

`retrievePassages` catches errors internally and never throws (returns `[]`). But `assembleContext` wraps the call in a try/catch and logs a failure entry:

```typescript
} catch (err) {
  blocks.push({ name: "voice-corpus", content: "", tokenCount: 0, truncated: false });
  await logRetrieval(sessionId, "voice-corpus", false, null, false, ...);
}
```

This catch block will never fire for retrieval errors since `retrievePassages` swallows them. The outer error handling gives a false sense of coverage — the only scenario it catches is a bug in the topic-derivation code above it (e.g., `decomposition.vocabulary` being `undefined`).

## Test coverage

Not tested: the API routes (no integration tests for POST/GET/PATCH/DELETE validation or error responses), the migration script against real WritingSample data, the `assembleContext` voice-corpus block integration, or the UI behavior.
