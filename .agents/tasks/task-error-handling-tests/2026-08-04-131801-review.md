# extractErrorMessage utility and client component fixes

This change introduces a shared `extractErrorMessage` utility that safely extracts displayable strings from API responses returning structured error objects `{ error: { code, message, requestId } }`, and retrofits 9 client components to use it instead of directly passing `data.error` (an object) to `setError` or `throw new Error` (which expect strings). The utility also handles legacy `{ error: "string" }` responses and falls back gracefully for null/undefined. A comprehensive 32-test suite covers the utility itself.

Watch for: The fix is incomplete — at least 8 additional call sites across `companies/page.tsx` (fetchCompanies), `company/[slug]/page.tsx` (loadCompany), `company/[slug]/DraftsTab.tsx`, `skills/page.tsx` (3 sites), `experience/page.tsx`, `jobs/page.tsx`, and `phrases/page.tsx` still use the raw `errData.error || "fallback"` pattern and remain vulnerable to the same "[object Object]" rendering bug (confirmed). Additionally, the `parse-responsibilities.ts` module — a pure-logic parser with no external dependencies — has zero test coverage, which is the exact class of untested code that let the original error-handling bug ship undetected.

**Verdict**: NEEDS_CHANGES

## High-level view

The fix only reached call sites where the variable was named `data`. Several other pages use `errData` as the variable name for the same pattern, and the grep in the feature's verification step (`setError(data.error` / `setError(data?.error`) would not catch those. This leaves the exact same class of bug live in production for skills, experience, jobs, phrases, company loading, and drafts pages.

The broader coverage gap flagged by the user — "this should have been caught by a test" — is only partially addressed. The project has no tests for `parse-responsibilities.ts` (pure logic, no deps), `parse-job.ts` (has DB dependency but the heuristic extractors are testable in isolation), and none of the client components have rendering tests that would catch "[object Object]" in error state.

## Incomplete migration across client components

The PR fixed 9 call sites but missed at least 8 more. The pattern across unfixed files is identical — a response is parsed with `await res.json().catch(() => ({}))` and then `errData.error` is passed directly to `setError()` or `throw new Error()`:

```typescript
// src/app/skills/page.tsx:77 (unfixed)
const errData = await res.json().catch(() => ({}));
setError(errData.error || `Failed to load taxonomy (${res.status})`);
```

When the API returns the structured `{ error: { code, message, requestId } }` format from `formatErrorResponse`, `errData.error` is an object, and the `||` fallback is never reached because objects are truthy. The result: `setError` receives `{ code: "...", message: "...", requestId: "..." }` and React renders it as "[object Object]".

The unfixed files: `companies/page.tsx` (the `fetchCompanies` loader on line 37 — distinct from the two fixed call sites for add/sync), `company/[slug]/page.tsx` (the initial `loadCompany` call on line 88), `company/[slug]/DraftsTab.tsx` (line 39), `skills/page.tsx` (three separate calls), `experience/page.tsx` (line 88), `jobs/page.tsx` (line 50), and `phrases/page.tsx` (line 189).

The pages that already use `data.error?.message` — `claims/page.tsx`, `documents/page.tsx`, `resume/page.tsx` — aren't actively buggy because they explicitly access `.message`, but they'd benefit from `extractErrorMessage` for consistency.

## Verification step misses the pattern

The feature's verification step runs:
```bash
grep -rn 'setError(data.error\|\|setError(data?.error' src/
```

This only matches when the variable is named `data`. Multiple pages use `errData` as their variable name for the parsed JSON response. A more complete check:
```bash
grep -rn '\.error\s*||' src/app/ src/components/ | grep -v extractErrorMessage | grep -v '\.error?.message'
```

## Test coverage gaps in pure-logic modules

`parse-responsibilities.ts` exports `parseResponsibilities` — a pure function that splits text into lines, strips bullet markers, detects section headers, removes known prefixes, validates action-verb starts, deduplicates, and annotates with keywords. It has multiple regex patterns, branching logic for section classification, and interacts with `parseSkills`. Zero tests exist for it. This is exactly the kind of module where edge-case bugs hide (section detection fails on slightly different header text, prefix stripping is too aggressive, etc.).

`parse-job.ts` has DB-dependent functions (`getRecentCorrections`, the outer `parseJob` that calls it), but `extractTitle`, `extractCompany`, `extractLocation`, and `contextSimilarity` are all pure heuristic functions that could be tested in isolation if exported or tested via the module's public API with corrections mocked.
