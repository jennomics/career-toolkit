# Packages, Eval Harness, and Export Gate

This change adds three major subsystems to the career toolkit: application packages (bundling generations into a multi-document unit with cross-document overlap detection), an evaluation harness (Tier 1 regression assertions, Tier 2 property checks, golden package runners, and known-bad anchor scoring), and an export gate that blocks package finalization when factual, confidentiality, or format requirements aren't met. The pipeline integration threads a `packageId` through generation so that overlap detection and claim-usage recording happen automatically at generation time.

Watch for: the golden package runner's fire-and-forget pattern in the API route loses errors silently and the returned `runId` is unrelated to any persisted record (confirmed); the `variance` field in metrics is actually standard deviation, not variance (confirmed); the Levenshtein implementation allocates O(n) arrays per character with no early-exit optimization, which will be slow for long documents in production golden package runs (confirmed).

**Verdict**: APPROVED

## High-level view

The package subsystem introduces `ApplicationPackage` as the container that groups generations for a single job application. Cross-document overlap detection queries existing `PackageClaimUsage` rows before each generation and returns an overlap report in the pipeline result. Nothing in this diff blocks generation when overlap is found — the report is purely informational, leaving the decision to the client.

The eval harness is structured as layered runners: Tier 1 (hard assertions from a DB table), Tier 2 (seven structural property checks that produce violations-per-1000-words), golden packages (LLM-regeneration with edit-distance comparison to a human-submitted version), and anchor scoring (known-bad texts that must fail property checks). Fact and voice scores are deliberately kept separate — a high voice score cannot compensate for a failing assertion.

The export gate runs four sequential checks (disposition, freshness, confidentiality, format) and short-circuits with structured blocking issues if any fail. Word count validation applies only to accepted (non-rejected) spans, which means rejecting spans during review can push a cover letter below the 250-word minimum with no recovery path other than regeneration.

The golden package API endpoint fires off the generation asynchronously and returns a UUID that is never stored anywhere — a client cannot correlate it with eventual EvalRun records.

<details>
<summary>Issues (5)</summary>

1. **Golden run ID disconnect** — `POST /api/eval/run` with `goldenPackageId` returns a `crypto.randomUUID()` that is never written to any database record. The client has no stable handle to poll for results. Either store the run ID as a batch identifier on the EvalRun rows, or return the actual EvalRun IDs after the run completes (making the endpoint synchronous or adding a batch record).
2. **Variance is actually standard deviation** — `metrics.ts` computes `Math.sqrt(...)` but names the field `variance`. Either rename to `stdDev` or remove the `sqrt` call to compute actual variance.
3. **Levenshtein on long documents** — `golden.ts` uses an O(m×n) character-level Levenshtein with no length guard. A 3000-character golden document produces a 9-million-iteration inner loop per run. Consider switching to a word-level diff or adding a length cap before falling back to a sampling approach.
4. **Assertion duplication in EvalRun storage** — `runner.ts` stores `tier1.results` in both `assertionResultsData.tier1` and `assertionResultsData.results` (identical arrays). This doubles storage for no added information.
5. **Anchor threshold sensitivity to short texts** — The fixed threshold of 2.0 violations per 1000 words means a 50-word anchor text needs only 0.1 violations to pass, making the harness appear broken on short inputs despite the text being genuinely bad. Consider a minimum word count for anchor texts or an absolute-violation floor.

## Golden package runner and the fire-and-forget gap

```typescript
// src/app/api/eval/run/route.ts
const runId = crypto.randomUUID();
runGoldenPackage(goldenPackageId).catch((err) => {
  console.error(`Golden package run ${runId} failed:`, err);
});
return NextResponse.json({ status: "started", runId, ... });
```

The `runId` returned to the client is generated locally and never stored. `runGoldenPackage` internally creates its own `EvalRun` records with Prisma-generated CUIDs. A client receiving `runId: "abc"` cannot query `/api/eval/results` for that identifier because it doesn't exist in the database. The fire-and-forget pattern also means any error (DB down, LLM timeout) is swallowed into stderr with no persistence.

## Metrics naming: variance vs. standard deviation

```typescript
const variance =
  editDistances.length > 1
    ? Math.sqrt(
        editDistances.reduce((sum, d) => sum + Math.pow(d - mean, 2), 0) /
          editDistances.length
      )
    : 0;
```

This computes the population standard deviation, not variance. The field is named `variance` in both the type declaration and the returned object. The dashboard displays it as "standard deviation of edit distances" — the label is correct but the field name isn't.

## Levenshtein performance on production-length documents

`golden.ts` implements a two-row O(m*n) character-level Levenshtein. At resume scale (~5000 chars) it becomes 25 million operations per run x 3 runs = 75 million iterations per golden package evaluation. No length guard or sampling fallback exists.

## Export gate: word count brittleness after span rejection

Format validation counts words from `gen.spans.filter(s => s.disposition !== "rejected")`. The cover-letter limit of 250-300 words is tight; rejecting even a single sentence-length span could drop below minimum. There's no mechanism to regenerate or fill the gap — the export fails with a blocking issue and the user must trigger a new generation cycle.

## ExhibitAdjacency silent pass on whitespace-normalized text

`exhibitAdjacency` uses a 30-character substring match (`span.text.trim().substring(0, 30)`) to locate spans within the rendered sentence list. If whitespace normalization during rendering changes the span boundaries (spans are joined with `" "` in export, and the pipeline renders with its own logic), the substring won't match and the check silently passes — no violation reported, no warning that the span couldn't be located.

## Test coverage gaps

Not tested: the `runFullEval` integration path (all tiers + golden + anchors combined), the async fire-and-forget behavior of the golden package API endpoint, the `exhibitAdjacency` substring-matching edge case, and concurrent overlap detection (two generations running simultaneously for the same package could both see zero overlap and both record the same claims — a race condition in the upsert-after-save pattern).
