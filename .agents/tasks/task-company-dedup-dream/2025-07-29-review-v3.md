# Company model, dedup system, and dream designators (v3)

This change adds a Company entity with CRUD, auto-linking from jobs, interactive deduplication for both companies and jobs, company detail pages with 7 scoped tabs (including LLM resume generation), and dream company/job visual designators with bidirectional propagation. The v1 review raised 5 issues and the v2 review raised 2 additional slug collision gaps. All 7 issues have been resolved.

**Watch for:** The `GET /api/jobs/duplicates` endpoint still loads the entire jobs table into memory for in-process grouping (likely) — this is the only remaining scaling concern, but it's on a user-initiated dedup path, not the hot path.

**Verdict**: APPROVED

## High-level view

Slug collision handling is now consistent across all four company-creation/rename paths: `POST /api/companies`, `POST /api/companies/sync`, `POST /api/jobs` (auto-create), and `PATCH /api/companies/[slug]`. Each uses a retry loop with numeric suffix fallback on P2002, and the job auto-create path additionally falls back to `findFirst` if all retries exhaust.

The `check-duplicate` endpoint no longer loads all jobs — it queries by `companyId` first, then falls back to a `contains` query on unlinked jobs. The company merge endpoint now consolidates `dreamCompany` status from merged companies into the survivor before deleting them.

The one remaining scaling concern is `GET /api/jobs/duplicates`, which calls `findMany` with no where clause and groups in memory. Acceptable for a single-user app with a user-initiated action, but will degrade past a few thousand jobs.

## Job duplicates endpoint scaling

```typescript
// GET /api/jobs/duplicates
const jobs = await prisma.job.findMany({
  include: {
    skills: { select: { id: true } },
    responsibilities: { select: { id: true } },
  },
  orderBy: { createdAt: "asc" },
});
```

This loads every job row plus relation IDs, then groups by normalized title+company and by description prefix in memory. At typical personal-tool scale (hundreds of jobs) this is fine. Past a few thousand rows, a DB-level `GROUP BY` on a normalized title column or cursor-based pagination would be appropriate.
