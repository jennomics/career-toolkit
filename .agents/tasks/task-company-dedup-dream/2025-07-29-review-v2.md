# Company model, dedup system, and dream designators (v2)

This change adds a Company entity with CRUD, auto-linking, interactive deduplication for companies and jobs, company detail pages with 7 scoped tabs (including LLM resume generation), and dream company/job visual designators with propagation logic. The v1 review raised five issues — slug collision handling, full table scan in check-duplicate, dream status lost on merge, a redundant index, and missing error handling in JobCard — all of which have been addressed in this revision.

**Watch for:** Slug collision handling is inconsistent across creation paths — the `POST /api/jobs` auto-creation path does not retry on P2002, unlike the company and sync endpoints (confirmed). The PATCH rename path can produce a slug that collides with an existing company and will throw unhandled (confirmed). The `GET /api/jobs/duplicates` endpoint still loads all jobs into memory for in-process grouping (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The P2002 retry loop was added to `POST /api/companies` and `POST /api/companies/sync`, but the third company-creation path — `POST /api/jobs` auto-creation — still calls `prisma.company.create` without collision handling. If two jobs with different raw company strings but identical slugs are created in sequence, the second will fail silently and leave the job unlinked. The PATCH endpoint for renaming a company regenerates the slug from the new name with no collision check at all, returning a 500 on conflict.

The check-duplicate endpoint's "likely" tier was rewritten to query by `companyId` first, eliminating the full-table-scan issue for linked companies. The `GET /api/jobs/duplicates` endpoint, however, still calls `prisma.job.findMany` with no where clause and groups in memory — a separate endpoint from the one fixed, but the same scaling pattern.

## Inconsistent slug collision handling across creation paths

The auto-creation path in `POST /api/jobs` wraps company creation in a try/catch that swallows the error with a console log:

```typescript
// src/app/api/jobs/route.ts
try {
  if (company && company.trim()) {
    // ...
    companyRecord = await prisma.company.create({
      data: { name: displayName, normalizedName, slug: slugify(displayName) },
    });
    // No P2002 handling here
  }
} catch (companyErr) {
  console.error("Failed to auto-link company:", companyErr);
}
```

The fail-open semantics prevent a user-facing error, but the company record silently fails to be created or linked. A user adding a job for a company whose slug collides with an existing different-normalized-name company will end up with an unlinked job and no indication of why. The same retry loop from `POST /api/companies` should be applied here.

The PATCH endpoint at `/api/companies/[slug]` recalculates the slug on rename without any collision handling — no try/catch, no retry, no pre-check. Renaming "Acme Corp" to "Meta" when a "meta" slug already exists will return a 500.

## LLM prompt construction with user-controlled notes

Company intelligence notes are interpolated directly into the LLM prompt in `generate-company/route.ts`:

```typescript
const companyIntelligence = company.notes
  ? `\n## COMPANY INTELLIGENCE\n...${company.notes}\n`
  : "";
```

In a single-user app this is self-injection only. The surface exists if the app ever becomes multi-user or imports notes from external sources.
