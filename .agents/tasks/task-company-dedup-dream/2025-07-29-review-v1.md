# Company model, dedup system, and dream designators

This change adds a Company entity layer atop the existing Job model, then builds out four capabilities on top of it: company CRUD with auto-linking, interactive deduplication for both companies and jobs, a company detail page with 7 scoped tabs (including company-scoped LLM resume generation), and dream company/dream job visual designators with propagation logic.

The approach is additive and non-destructive: `companyId` on Job is nullable, existing jobs continue to work without a linked company, and a sync endpoint back-fills the association. Company normalization strips corporate suffixes for dedup matching. The LLM resume endpoint gracefully degrades to a template when no API key is available.

**Watch for:** Slug collision on company create/sync can throw unhandled unique-constraint errors (confirmed). The `check-duplicate` endpoint loads the entire jobs table into memory for normalized matching (confirmed). Company merge does not consolidate `dreamCompany` state from merged records into the survivor (confirmed).

## High-level view

The schema adds a Company model linked to Job via a nullable `companyId` foreign key. The relation field is named `companyRef` to avoid collision with the existing `company: String` field on Job, so two representations of "company" coexist on the model: the denormalized string and the relational FK. The merge endpoint keeps them in sync by updating both `companyId` and the `company` string when reassigning jobs.

Company normalization strips one corporate suffix and lowercases for comparison. The slug is derived from the display name via a simple alphanumeric-replace slugifier with no collision avoidance. Two companies whose display names normalize to the same slug will fail at the DB unique constraint, and neither the POST /api/companies endpoint nor the sync endpoint handles that conflict gracefully.

The dedup system groups companies by `normalizedName` and jobs by normalized-company+title or first-200-chars of description. Merging uses `Promise.allSettled` correctly throughout. The check-duplicate endpoint's new "likely" tier fetches all jobs with `findMany` (no filter) and iterates in memory—a full table scan on every new-job submission.

Dream designation propagates from Job to Company on toggle, but the company merge endpoint does not consolidate dream status from merged companies into the survivor. Merging a dream company into a non-dream company silently drops the designation.

<summary>Issues (5)</summary>

1. **Slug collision on company create** — `slugify(displayName)` can produce duplicate slugs (e.g. "Meta Inc" and "Meta LLC" both slug to "meta"). Neither the POST /api/companies route nor the sync endpoint catches the unique-constraint violation; it bubbles as a 500. Add collision detection with a suffix or catch the Prisma P2002 error and retry with a numeric suffix.
2. **Full table scan in check-duplicate** — The "likely" confidence tier calls `prisma.job.findMany()` with no where clause and iterates all jobs in memory. Replace with a DB-level query on a new `normalizedTitle` indexed column, or at minimum add a where clause filtering by `companyId` after resolving the normalized company.
3. **Dream status lost on company merge** — `POST /api/companies/merge` moves jobs and deletes merged companies but never checks if any merged company had `dreamCompany=true`. If the survivor is not a dream company but the merged ones were, the flag disappears. Add `if (any merged company is dreamCompany) set keepCompany.dreamCompany = true`.
4. **Redundant index on slug** — The Company model declares both `@unique` on slug and `@@index([slug])`. The unique constraint already creates an index; the explicit `@@index` is dead weight. Remove the `@@index([slug])` line.
5. **No error handling on dream toggle fetch failures in JobCard** — `handleToggleDreamCompany` and `handleToggleDreamJob` have `try/finally` but no `catch`. If the fetch rejects (network error), the promise rejection is unhandled. Add a catch clause that surfaces the error or at minimum swallows it explicitly.

## Slug collision and normalization gap

The `slugify` utility produces deterministic output but has no awareness of existing slugs in the database. Two companies with different original names but identical post-normalization display names collide:

```
"Meta, Inc."  -> displayName: "Meta"  -> slug: "meta"
"Meta, LLC"   -> displayName: "Meta"  -> slug: "meta"
```

The POST /api/companies route checks for duplicate `normalizedName` and returns 409, which catches this specific case for direct creation. The sync endpoint processes groups by normalizedName so won't create two records for the same normalized name. The real risk is two companies with *different* normalizedNames that happen to produce identical slugs after the regex transform. The DB will throw `P2002` and the sync batch will partially fail with no user-visible explanation beyond a generic 500.

## Full-table job load in check-duplicate

```typescript
// In /api/jobs/check-duplicate - Check 2
const allJobs = await prisma.job.findMany({
  select: { id: true, title: true, company: true, createdAt: true },
});
```

This loads every job row to compare normalized titles and companies in a loop. The endpoint is called on every job creation (from AddJobForm), so it's on the hot path. A database-level approach using a stored normalized column with an index, or at minimum filtering by resolved `companyId` first, would avoid linear growth.

## Dream status propagation asymmetry

The dream toggle endpoint (`/api/jobs/[id]/dream`) correctly propagates to the linked Company when toggling a single job. The company merge endpoint, however, moves jobs and deletes merged companies without inspecting their `dreamCompany` flag:

```typescript
// /api/companies/merge - after moving jobs and deleting companies
// Missing: if any mergeId company had dreamCompany=true, set it on keepCompany
```

A user who marks "Anthropic, Inc" as a dream company and later merges it into "Anthropic" (the survivor) will lose the dream designation unless the survivor was independently marked.

## LLM prompt construction with user-controlled notes

The company intelligence notes field is interpolated directly into the LLM prompt:

```typescript
const companyIntelligence = company.notes
  ? `\n## COMPANY INTELLIGENCE\n...${company.notes}\n`
  : "";
```

For a single-user application this is self-injection only. If notes are ever imported from external sources or the app becomes multi-user, this unescaped interpolation becomes a prompt injection vector.

## Test coverage

No test framework exists in this project. Not tested: slug collision behavior, dream propagation on merge, normalized title matching edge cases (e.g. "Sr." vs "Senior" vs "Staff" permutations), company sync with hundreds of jobs, concurrent merge operations on the same group.
