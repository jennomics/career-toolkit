# Full-stack job application tracker with pipeline board, analytics, and CRUD

This change adds a complete job application tracking system spanning schema, API, and UI. Five new Prisma models (ApplicationEvent, Interview, Contact, JobContact, FollowUp) and six new fields on Job power twelve new API routes under `/api/tracker/`. The UI delivers a kanban pipeline board with drag-and-drop status transitions, a sortable list view with bulk actions and CSV export, a timeline of application events, an analytics dashboard with conversion funnel visualization, and a detail drawer with tabbed CRUD for interviews, contacts, follow-ups, and documents. Status changes on PATCH `/api/jobs/[id]` now auto-log ApplicationEvents.

Watch for: inconsistent ARCHIVED_STATUSES definitions between tracker-helpers (includes "accepted") and jobs/page.tsx + JobCard.tsx (does not) [confirmed]; the attention route hard-codes its own active status list rather than importing ACTIVE_STATUSES from the shared helpers [confirmed]; the pipeline route fetches all jobs including followUps and skills regardless of whether the client needs them [confirmed]; no duplicate-link prevention on the job-contacts POST endpoint [confirmed].

**Verdict**: APPROVED

## High-level view

The auto-logging design fires after the job update succeeds and swallows event-creation failures, so it cannot break the primary write path — but the timeline can have gaps under DB load with no retry mechanism.

The pipeline board uses native HTML5 drag-and-drop with an ARIA live region and Ctrl+Arrow keyboard shortcuts. It re-renders after the PATCH round-trip rather than optimistically updating, so the board always reflects server state at the cost of a brief lag on drop.

The analytics dashboard computes conversion rates using a cumulative "at-or-beyond" snapshot model rather than tracking actual transitions. Rejected and withdrawn jobs don't reduce the denominator for earlier stages, which produces inflated rates as the dataset grows. The ApplicationEvent history already exists to power a flow-based calculation.

Bulk actions in the list view use `Promise.allSettled` to fire parallel PATCH/DELETE requests per job. For small selections this is fine; at scale it will hammer the API with N concurrent requests without throttling.

<summary>Issues (5)</summary>

1. **ARCHIVED_STATUSES inconsistency** — tracker-helpers includes "accepted" but jobs/page.tsx and JobCard.tsx do not. A job with status "accepted" appears active on the Jobs page but archived in the Pipeline board. Align all three definitions or import from the shared module.
2. **Attention route hard-codes active statuses** — `/api/tracker/attention` defines its own `activeStatuses` array instead of importing from tracker-helpers. If the status vocabulary changes, these will drift. Import from the shared source and filter further if "saved"/"researching" should be excluded.
3. **Pipeline route over-fetches** — GET `/api/tracker/pipeline` includes skills and followUps relations for every job. The PipelineBoard only uses the TrackerJob scalar fields. Drop the includes or add a select clause.
4. **No duplicate-link guard on job-contacts** — POST `/api/tracker/job-contacts` doesn't check if the contact is already linked to the job, so duplicate links can be created. Add a unique constraint on (jobId, contactId) or a pre-check.
5. **Bulk actions unbounded concurrency** — ListView fires N parallel fetch calls for bulk operations. Add batching or a server-side bulk endpoint if list sizes grow.

## Auto-logging gap risk

The event creation happens outside the job update — they're separate queries, not a transaction:

```typescript
if (status !== undefined && status !== currentJob.status) {
  try {
    await prisma.applicationEvent.create({ ... });
  } catch (eventErr) {
    console.error("Failed to create status change event:", eventErr);
  }
}
```

If the event write fails, the status change still succeeds and the failure is only logged to console. The timeline can silently miss transitions under DB pressure with no retry or dead-letter mechanism.

## ARCHIVED_STATUSES drift

Three definitions exist:

| Location | Includes "accepted"? |
|----------|---------------------|
| `tracker-helpers.ts` | Yes |
| `jobs/page.tsx` | No |
| `JobCard.tsx` | No |

A job with status "accepted" appears in the "active" view on the Jobs page but won't show in the Pipeline board's active columns. The tracker-helpers definition is the authoritative one for the new system; the Jobs page and JobCard should import from it or be aligned.

## Attention route vs shared constants

The attention route hard-codes:
```typescript
const activeStatuses = ["applied", "screening", "interviewing", "final-round", "offer", "negotiating"];
```

`ACTIVE_STATUSES` in tracker-helpers yields `["saved", "researching", "applied", "screening", "interviewing", "final-round", "offer", "negotiating"]`. The route intentionally excludes "saved" and "researching" (you haven't applied yet, so staleness doesn't apply), but this intent is undocumented. If a new pre-application status is added to the vocabulary, the attention route won't automatically adapt. Import from the shared source and filter, or add an explicit comment.

## Pipeline route payload weight

```typescript
const jobs = await prisma.job.findMany({
  include: { skills: true, followUps: true },
  orderBy: { updatedAt: "desc" },
});
```

PipelineCard uses only: id, title, company, status, priority, nextAction, nextActionDate, appliedAt, updatedAt, createdAt, salary, location. Skills and followUps arrays are sent over the wire but never rendered. For a user with 100 jobs and 5 skills each, that's 500 extra skill objects per pipeline load.

## Conversion rate inflation

`computeConversionRates` uses a cumulative snapshot:

```typescript
const fromCount = activeOrder.slice(i).reduce((sum, s) => sum + (stageCounts[s] || 0), 0);
const toCount = activeOrder.slice(i + 1).reduce((sum, s) => sum + (stageCounts[s] || 0), 0);
```

Jobs rejected or withdrawn from mid-pipeline stages leave the count entirely (they're in separate buckets not included in `activeOrder`), making conversion appear higher than reality. With 50 applied and 25 rejected from screening, the "applied to screening" rate won't reflect the 25 that fell out. The ApplicationEvent history already exists and could power an accurate flow-based calculation.

## Bulk delete accessibility

The bulk delete confirmation uses `window.confirm`, which blocks the main thread and isn't reliably announced by screen readers. A custom confirmation modal with focus management would maintain the accessibility standard set by the rest of the UI.

## Test coverage gaps

Not tested: API route handlers (would require integration tests), the auto-logging trigger on status change, component rendering, drag-and-drop interactions, bulk action error paths, attention query correctness at the database level, or the duplicate-link scenario on job-contacts.
