# Candidate Profile: structured resume-writer intake backed by Prisma + Next.js API

This change adds a full candidate profile subsystem to the career-toolkit app: six new Prisma models forming a one-to-many star schema off `CandidateProfile`, seven API route files exposing CRUD operations, a React page at `/profile` with component-per-section architecture, and a seed script pre-populating a complete executive profile. The design is single-tenant today with profileId relations enabling multi-user later. The approach is straightforward data-driven CRUD — no auth, no optimistic UI, no background sync.

Watch for: the `|| null` coercion pattern in the profile PUT route silently drops empty strings and falsy values (confirmed), the generation-ready endpoint reports `ready: true` when zero unresolved items exist even if the profile is otherwise incomplete (confirmed), roles cannot be edited after creation — only created or deleted (confirmed), and there is no authorization on any endpoint (likely intentional for single-tenant, but worth a line of defense if this ever goes multi-user).

**Verdict**: APPROVED

## High-level view

The Prisma schema adds six models with cascade deletes, `@@index` on every foreign key, `String[]` for list fields, nullable for optional content. The `priority` field on `UnresolvedItem` is a free string rather than an enum — the seed data and UI constrain it to `high`/`medium`/`low` but the database accepts anything.

The API layer follows the existing jobs route pattern — lazy prisma proxy, try/catch everywhere, error messages in the response body. The profile route uses a find-first-then-upsert pattern since there's no auth and only one profile exists. Sub-resource routes require `profileId` as a query param on GET and in the body on POST, creating an asymmetry with the main profile route that fetches without any identifier.

The UI is a single page composed of ~10 section components sharing a common pattern: local state, fetch on action, `onRefresh` callback to reload the parent. Error display happens at both the page level (for profile-wide saves) and within each section (for sub-resource operations). The unresolved-items section opens by default when items are unresolved and includes a warning banner.

<details>
<summary>Issues (5)</summary>

1. **Falsy-value coercion in profile PUT** — `email || null`, `phone || null` etc. means saving an empty string intentionally is impossible, and any field that evaluates to falsy (e.g. `""` becomes null silently). Use explicit `=== undefined` checks or accept the body as-is after validation.
2. **Roles and metrics have no PUT/edit endpoint** — Career roles and profile metrics can be created and deleted but not updated in-place. The spec calls for inline editing on the UI; currently a user must delete and re-create to fix a typo.
3. **Generation-ready semantics are loose** — The endpoint returns `ready: true` when `totalItems === 0`, which means a brand-new empty profile reports as generation-ready. Consider requiring at minimum that unresolved items exist and are all resolved.
4. **No authorization layer** — Every route is open. Acceptable for single-tenant personal tooling, but if profileId relations are the multi-user prep, a middleware guard mapping session to profileId should be the next step before any deployment beyond localhost.
5. **CollapsibleSection aria-controls references a missing element** — When collapsed, children are removed from the DOM entirely, so the `aria-controls` attribute on the toggle button points to a nonexistent `id`. Screen readers tolerate this, but it's an ARIA validity gap.

## Falsy-value coercion in the profile upsert

The PUT handler at `src/app/api/profile/route.ts` builds a `data` object by applying `|| null` to every optional field:

```typescript
location: location || null,
phone: phone || null,
email: email || null,
```

This treats empty strings, `0`, and `false` identically to `undefined` — they all become `null`. It's a latent bug: if any field is ever extended to accept `0` or `false` as a valid value, this pattern silently drops it. A user explicitly clearing a field by blanking it would get null stored rather than empty string. A safer pattern: `location !== undefined ? location : null` or simply passing the body through after stripping `undefined` keys.

## Missing PUT on roles and metrics

The spec requests inline editing for career roles. `src/app/api/profile/roles/route.ts` implements GET, POST, and DELETE but not PUT. The same gap exists for `metrics/route.ts`. The CareerTimelineSection component only offers "Add Role" and "Delete" buttons — a user who needs to fix a typo in a highlight bullet or update a sort order must delete and recreate the entire role.

Stories and unresolved items both have PUT handlers, so this appears to be an oversight rather than a deliberate omission.

## Generation-ready endpoint edge cases

```typescript
ready: totalItems === 0 || unresolvedCount === 0,
```

The condition `totalItems === 0` makes an empty profile pass the readiness check. If this endpoint gates resume generation downstream, a newly-created profile with no unresolved items will appear generation-ready even though it has no content. The semantic might be better expressed as: ready when `totalItems > 0 && unresolvedCount === 0`, with an explicit "no items yet" state distinguished from "all items resolved."

## CollapsibleSection conditional rendering

```tsx
{isOpen && (
  <div id={contentId} className="...">{children}</div>
)}
```

The button's `aria-controls={contentId}` references an element that doesn't exist in the DOM when collapsed. Additionally, any child component holding ephemeral state (like an in-progress form) will lose that state if the user collapses and re-opens. This is a constraint for future development — currently each section manages its own state independently so nothing is lost.
