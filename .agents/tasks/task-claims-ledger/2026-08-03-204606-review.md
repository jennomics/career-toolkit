# Claims Ledger with Evidence Model and Correction Flow

Adds a canonical facts layer to the career toolkit: claims (what generation is allowed to say), artifacts (where a fact was observed), negative assertions (what must never be generated), and a correction flow that updates a claim while blacklisting its old wording. The implementation spans Prisma schema, five API route files, a seed script, and a single-page React UI.

Watch for: The correction "atomicity" is three sequential DB writes without a `$transaction`, so a mid-operation failure leaves the claim in an inconsistent state (confirmed). The `@@unique([claimKey, status])` constraint will throw a Prisma unique violation (not a 409) when the seed script or any caller tries to create two "unverified" claims with the same claimKey (confirmed). The UI modal lacks focus trapping, so keyboard-only users can tab behind the overlay (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The `@@unique([claimKey, status])` compound constraint prevents duplicate claim+status pairs but does not prevent duplicates across different statuses. It interacts poorly with the soft-delete pattern: transitioning two claims with the same claimKey to "superseded" will fail on the second one. More critically, when the application-level findFirst guard is bypassed (race condition), the DB throws P2002 which maps to 500 rather than the intended 409.

The correction endpoint performs three independent writes (update claim, create correction, create negative assertion) without wrapping them in a Prisma `$transaction`. If any write after the first fails, the claim statement has already been modified but the correction record or negative assertion is missing, leaving the system in a state that the idempotency guard won't recover from.

The seed script's claimKey for highlights truncates to 80 slug characters, so different highlights with long shared prefixes will silently collide — the second highlight is skipped by the findFirst guard and its data is lost.

The UI's correction modal lacks focus trapping and return-focus-on-close, failing WCAG 2.1 AA requirements for modal dialogs. The per-card conflict indicator counts superseded claims in its conflict group, producing false-positive conflict warnings after a claim has been soft-deleted.

<summary>Issues (6)</summary>

1. **Correction non-atomicity** — Wrap the three writes in `prisma.$transaction([...])` so a failure in step 2 or 3 doesn't leave the claim updated without a matching correction/assertion record.
2. **Unique constraint vs. conflict detection mismatch** — The `@@unique([claimKey, status])` constraint means two "unverified" claims with the same key trigger a Prisma P2002 error (500), not the intended 409. Either catch P2002 and map it to 409, or remove the unique constraint in favor of application-level enforcement only.
3. **Unique constraint blocks multiple soft-deletes** — Two claims sharing a claimKey cannot both be set to "superseded" because of `@@unique([claimKey, status])`. The DELETE handler will 500 on the second one.
4. **Slug truncation collisions in seed** — `slugify(highlight.text).slice(0, 80)` can produce identical claimKeys for different highlights that share long prefixes. Append a discriminator (e.g., the highlight ID suffix) or hash the full text.
5. **Modal focus trap missing** — The correction modal does not trap focus; keyboard users can tab to elements behind the overlay. Add a focus-trap (or `inert` on the background) and restore focus to the trigger button on close.
6. **False-positive conflict warnings** — The per-card conflict check counts superseded claims in its group, showing conflict warnings for resolved claims. Filter `claimsByKey` to non-superseded before passing to `ClaimCard`.

## Correction flow lacks transactional guarantee

The `/api/claims/[id]/correct` handler executes three sequential Prisma calls:

```typescript
const updatedClaim = await prisma.claim.update(...);
const correction = await prisma.claimCorrection.create(...);
const negativeAssertion = await prisma.negativeAssertion.create(...);
```

If step 2 or 3 throws (connection drop, constraint violation), the claim's `statement` has already been modified. The idempotency guard only triggers when `claim.statement === correctedValue` AND both the correction and assertion exist. A partial failure leaves the claim updated with no correction record, and the next retry would see `statement === correctedValue` but fail the idempotency check (missing correction), falling through to create another update — which is a no-op on the claim but creates orphan records.

Prisma 7 supports `prisma.$transaction([...])` with the PrismaPg adapter. Wrap all three operations in a transaction.

## @@unique([claimKey, status]) creates multiple failure modes

The schema declares `@@unique([claimKey, status])` on Claim. The constraint creates three distinct problems:

**Race condition on create:** The conflict detection in POST /api/claims uses `findFirst({ where: { claimKey, status: { not: "superseded" } } })`. If the findFirst is bypassed (concurrent request passes the check before the first insert commits), the DB throws P2002 which `formatErrorResponse` maps to a generic 500. The API should catch P2002 specifically and return 409.

**False safety net:** Creating a "verified" claim when an "unverified" one with the same key exists is correctly caught by findFirst (returns 409), but the unique constraint would *not* prevent this at the DB level (different status values). The constraint doesn't protect the case it's designed for.

**Soft-delete collision:** If two claims share a claimKey and you try to soft-delete both (set status to "superseded"), the second DELETE will fail because `@@unique([claimKey, status])` already has a row for that key+superseded pair. This makes the soft-delete pattern fail for the exact scenario the system surfaces to users (conflicting claims on the same key).

## Seed slug truncation can produce duplicates

```typescript
const claimKey = `highlight-${slugify(highlight.text).slice(0, 80)}`;
```

Two different highlights whose text produces the same first 80 slug characters will collide. The `findFirst` guard prevents a crash (it skips), but the second highlight is silently dropped. Experience highlights often start with similar phrases ("Led the development of...", "Led the implementation of..."), making this a plausible data-loss scenario. Appending the highlight's CUID or a short hash of the full text would differentiate them.

## Conflict detection includes superseded claims in per-card count

`claimsByKey` is built from the full claims array including superseded claims:

```typescript
const claimsByKey: Record<string, Claim[]> = {};
for (const claim of claims) {  // includes all statuses
  claimsByKey[claim.claimKey] ??= [];
  claimsByKey[claim.claimKey].push(claim);
}
```

In `ClaimCard`: `{conflicts.length > 1 && <ConflictWarning claims={conflicts} />}` fires if a superseded sibling exists. The summary bar's `hasConflicts` correctly filters to non-superseded, but the per-card check does not — creating an inconsistency where individual cards show conflict warnings that the top-level summary bar would not flag.

## Modal accessibility

The correction modal does not implement focus trapping — pressing Tab cycles through the entire page DOM rather than being constrained to the modal. There is no mechanism to return focus to the "This is wrong" button that triggered it. For WCAG 2.1 AA compliance (which the spec's accessibility requirement implies), both focus trap and focus restoration are needed.
